# 自动化恢复检查点（2026-11-06）

本轮改进任务编排源码，解决 AI 规划中断后重复调用及旧执行覆盖状态的问题。它不是完整无人值守选品、作图或刊登的交付，也没有修改生产数据、部署服务或调用真实模型和 ERP。

## 已实现

- 开始 AI 规划前，以 SQLite 事务保存尝试 ID、输入校验值和“已开始”状态；提交失败时不调用模型。
- 合法结果先保存到任务检查点，再推进任务阶段。若在两者之间中断，核对后复用已保存结果，不重新调用模型。
- 超时、格式错误、未知结果，以及旧版只有开始记录而无可核对检查点的任务，继续停在“需核对”。普通对账文字不能清除尝试记录或授权自动重发。
- 启动时生成独立执行 ID；工具前、结果落账和异常落账均检查执行身份和状态。旧执行不会覆盖新任务状态或继续推进阶段。
- 已完成规划在“更新资料重检”时保留，只重新检查后续免费步骤。原有图片提交保护、预算预留和 ERP 回执保护保持不变。
- 检查点不改变费用事实：费用未知仍为未知，不写为零，也不宣称预算硬封顶。
- 任务列表和下载报告不暴露内部规划结果副本或工作台快照；正常规划摘要仍由任务结果展示。

## 使用及边界

一个账号数据目录目前只支持一个工作台服务实例。不要把同一 SQLite 数据目录放到共享盘上供多台电脑同时运行。新的事务及执行 ID 是防重复和防旧结果覆盖措施，不等于已支持多机分布式队列。

“需核对”的未知调用需要保留原始响应、服务商账单和执行记录，不可删除尝试、另建店铺档案或另建任务来绕过。当前没有对未知调用自动判定“未发生”的功能。若已记录工具开始但检查点写入失败，即使测试确认没有调用模型，系统仍保守停止，不支持自动续跑。

完整自动化仍缺：持续选品与货源浏览器执行器的统一接入、全套图片成本及重试策略、目标店铺新品草稿及发布回读、CLI 与网页任务台账统一。各能力保持未完成标记。产品库保存、本地预检、模拟测试不代表刊登完成或 Amazon 在售。

## 隔离验收

新增 test_workflow_recovery.py 覆盖超时、非法模型输出、落盘失败、结果保存后中断、校验失败、旧任务、重检、账号隔离、旧执行写回和两个独立进程争抢同一规划。

测试全部使用临时账号与合成产品；模型模拟，外部网络阻断。扩大回归及数量见 outputs/workflow-recovery-20261106/verification.json 和 pipeline-verification.json。

本轮源码不会自动更新既有生产 EXE 或旧便携 ZIP。发布前应重新打包并按对应版本验收；另一台实体电脑的首次启动仍需要独立验证。
